# Полный цикл сборки и установки

`scripts/ci.sh` выполняет практику №5 на нативной ОС: получает заданную версию исходников из Git, собирает приложение, запускает unit- и widget-тесты, создаёт установщик, устанавливает его и проверяет запуск установленного приложения. Установщик для практики №4 описан в [packaging.md](packaging.md).

## Подготовка

Нужны Git, Bash, FVM и нативные инструменты из [README](../README.md#нативные-инструменты). Скрипт использует `fvm install`, затем `fvm flutter`; версия закреплена в `.fvmrc`. Каталог, откуда вызвана команда, не сбрасывается и не очищается.

Дополнительно нужны:

| ОС | Инструменты упаковки и проверки | Установка приложения |
| --- | --- | --- |
| macOS | Штатные `pkgbuild`, `productbuild`, `installer`, `codesign` | `~/Applications/Abacus.app`, без `sudo` |
| Windows | Git Bash, PowerShell 7 (`pwsh`), Inno Setup 6 (`ISCC.exe` в `PATH`) и C++ runtime из Visual Studio | `%LOCALAPPDATA%/Programs/Abacus`, без прав администратора |
| Ubuntu/Debian | `dpkg-dev`, `xvfb`, `xauth`; `sudo` для установки `.deb` | `/opt/abacus`, команда `/usr/bin/abacus` |

На Ubuntu/Debian дополнительные инструменты:

```sh
sudo apt-get update
sudo apt-get install -y dpkg-dev xvfb xauth
```

Сборка и установка выполняются на соответствующей ОС: Mac не создаёт Windows-установщик. Скрипты установки отказываются заменять существующий Abacus, чтобы не перезаписать пользовательскую установку. Перед повторной установкой удали предыдущую штатным способом из [инструкции](packaging.md). Исходники и журналы прошлых запусков сохраняются.

## Локальный полный запуск

Из checkout с этими скриптами:

```sh
bash scripts/ci.sh --ref main
```

По умолчанию используется `https://github.com/prankerborislavchik/abacus.git`, текущая ОС и новый временный каталог. Установка действительно выполняется на этой машине. Для воспроизводимого запуска вместо движущейся ветки передай SHA:

```sh
bash scripts/ci.sh \
  --repository https://github.com/prankerborislavchik/abacus.git \
  --ref <commit-sha> \
  --target macos \
  --work-dir "$HOME/abacus-ci-review"
```

`--work-dir` должен ещё не существовать. На Windows та же команда запускается из Git Bash с `--target windows`, на Linux — с `--target linux`. Если FVM не используется, флаг `--system-flutter` разрешает SDK из `PATH`; несовпадение с `.fvmrc` останавливает запуск.

Для проверки ещё не опубликованного коммита разработчик может указать локальный Git-репозиторий через `--repository /absolute/path/to/abacus --ref <commit-sha>`. При этом копируется только закоммиченная версия. Такое выполнение проверяет цепочку установки, но для демонстрации получения актуального кода с GitHub используй удалённый URL, как в CI.

Последовательность в скрипте:

1. `git clone --no-checkout`, `git fetch origin <ref>`, `git checkout --detach FETCH_HEAD` в новом каталоге `source/`; SHA записывается в журнал.
2. Проверка версии SDK и `flutter pub get --enforce-lockfile`.
3. `flutter build <target> --release` и `flutter test --reporter expanded`. Ошибка останавливает цикл до создания и установки пакета.
4. Вызов `scripts/package.sh` или `scripts/package-windows.ps1`, запись SHA-256 созданного файла.
5. Вызов `scripts/install.sh` или `scripts/install-windows.ps1`, проверяющих нативную установку и её файлы.
6. Запуск исполняемого файла из установленного каталога на пять секунд; процесс должен оставаться живым. Проверка завершает только свой процесс.

Linux без `DISPLAY` использует Xvfb. macOS запускает `~/Applications/Abacus.app/Contents/MacOS/Abacus`; Windows — `%LOCALAPPDATA%/Programs/Abacus/abacus.exe`; Linux — `/opt/abacus/abacus`. Тем самым проверяется именно установленная копия, а не файл из `build/`.

## GitHub Actions

[Checks](../.github/workflows/checks.yml) запускается при PR, push в `main` и вручную (`workflow_dispatch`). `Quality` проверяет форматирование, анализ и тесты. Только после его успеха параллельно выполняются `Install (macos)`, `Install (windows)` и `Install (linux)`.

Каждый native job подготавливает инструменты и вызывает тот же `scripts/ci.sh` с GitHub URL и точным `${{ github.sha }}`. Для PR это проверяемый merge commit GitHub; при push — commit ветки. Таким образом, workflow и локальная команда используют один порядок операций и одинаковые проверки. SDK action читает `.fvmrc`; сторонние actions закреплены полными SHA. Разрешение workflow — только `contents: read`, учётные данные checkout не сохраняются.

Artifacts хранятся 14 дней:

- `abacus-<os>-installer`: установочный пакет из `source/dist/` после успешной проверки установки и запуска.
- `abacus-<os>-evidence`: `run.txt` (запрошенный ref, фактический commit, время и код выхода), `pipeline.log`, версия SDK, `tests.log`, `package-sha256.txt`, `smoke.txt` и вывод приложения. Журналы выгружаются также после ошибки, если цикл успел создать их.

Результат `passed` в `smoke.txt` означает, что запущенный из установленного каталога процесс оставался живым пять секунд. Это ограниченная автоматическая проверка запуска. Она не проверяет клики, содержимое окна, расчёты через UI, клавиатуру или поведение на компьютере другого участника. Расчёты и виджеты отдельно проверяются Flutter-тестами; полноценный нативный показ команды остаётся ручной проверкой.

## Демонстрация практик

Для практики №4 скачай установщик соответствующей ОС, покажи нативную установку и запусти Abacus из установленного места. Пакеты не подписаны доверенным сертификатом распространителя; macOS-пакет не прошёл notarization. Автоматизация не меняет Gatekeeper, SmartScreen или системные настройки безопасности. Особенности установки учебного пакета описаны в [packaging.md](packaging.md).

Для практики №5 открой зелёный запуск Actions нужного commit и его журналы: получение кода, сборка, тесты, пакет, установка и запуск должны завершиться успешно. Сопоставь commit в `run.txt` и SHA-256 пакета с демонстрируемой версией. Самостоятельная и итоговая работы используют этот же YAML и установщик. Успешный workflow подтверждает техническое выполнение цепочки, а приёмка преподавателем учитывается отдельно.
