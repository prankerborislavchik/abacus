# Работа над Abacus

## Issue → ветка → PR → ревью → merge

Задача и критерии готовности живут в GitHub Issues. Для небольшой команды достаточно issue с ответственным и связанного PR; отдельная доска пока не нужна. Статус виден по этой паре: issue без PR — задача ещё не вынесена на ревью, draft PR — работа идёт, готовый PR — ждёт ревью, закрытый после merge issue — готово.

1. Уточни критерии issue и назначь себя ответственным.
2. Создай короткую ветку от актуального `main`, например `feat/12-expression-validation`.
3. Делай небольшие содержательные коммиты. Реализованную функцию фиксируй в Git вместе с её проверками.
4. Открой PR в `main`. Для полностью выполненной задачи добавь `Closes #12`; для частичного шага — обычную ссылку на issue, чтобы он оставался открытым.
5. Передай готовый PR на ревью. PR участников ревьюит Борис; для его собственного функционального PR нужен другой участник. Начальную настройку Борис может слить сам.
6. Исправь замечания, дождись успешных проверок и хотя бы одного одобрения другого участника. Используй **Create a merge commit**: коммиты участников должны сохраниться.

### Почему это trunk-based development

`main` — единственная общая интеграционная ветка, которую поддерживаем в собираемом состоянии. Ветки живут недолго: ориентир — один-два дня, изменения попадают в `main` часто. Большую задачу разбиваем на небольшие PR с работающими промежуточными состояниями.

Само правило «ветка на тикет» ещё не делает процесс trunk-based: важны короткий срок жизни ветки и частая интеграция. Rebase помогает обновить свою ветку; это инструмент, а не определение процесса. Подробнее: [Short-Lived Feature Branches](https://trunkbaseddevelopment.com/short-lived-feature-branches/).

Пример для обычного clone:

```sh
git fetch origin
git switch -c feat/12-expression-validation origin/main
# Работа, проверки и коммиты
git push -u origin feat/12-expression-validation
```

Перед завершением PR обнови свою ветку:

```sh
git fetch origin
git rebase origin/main
# Снова запусти проверки
git push --force-with-lease
```

Последняя команда нужна после rebase уже опубликованной **своей** ветки. Для общей ветки сначала договоритесь с её участниками. `main` не переписываем. В другом репозитории имя remote/default branch нужно проверить; `origin/main` — настройка этого проекта.

Worktrunk обязателен для агентов по [инструкции](agents/worktrees.md). Участникам команды достаточно обычных Git-веток.

## Unit-тесты и приёмка

Для **валидации выражения**, **вычисления по `=`** и **работы с памятью** unit-тесты входят в ту же задачу и PR, что и реализация. Проверяем публичное поведение чистых Dart-функций/классов; вывод предупреждения на экран не заменяет проверку валидатора.

У каждой такой задачи до реализации должны быть:

- границы поведения и согласованные правила;
- конкретные входные данные/действия и ожидаемый результат;
- обычные, граничные и ошибочные случаи;
- требование добавить unit-тесты и подключить поведение к интерфейсу.

Направления для будущих критериев (точные ответы определяются в соответствующих issues):

| Задача | Что проверять unit-тестами |
| --- | --- |
| Валидация | Допустимые выражения, пустая строка, неизвестные символы, незавершённая запись, скобки; корректное объяснение отказа |
| `=` | Каждая поддерживаемая операция, согласованные приоритеты и скобки, границы допустимых значений и вычислительные ошибки |
| Память | Последовательности операций, чтение/изменение/очистка и независимость от выражения согласно согласованному контракту |

Тесты размещаем в `test/calculator/`, файлы называем `*_test.dart`. Используем `test`, `group` и `expect` из `package:flutter_test/flutter_test.dart`; запуск — `fvm flutter test`. Проверка арифметики или состояния памяти обычно не требует `testWidgets`.

На этапе графического каркаса тестовых файлов нет. Первый PR с функциональностью добавляет настоящие тесты и шаг `flutter test` в существующий job `Quality` в CI. После этого он остаётся обязательной частью проверки всех PR. UI сейчас проверяем запуском, изменением размера окна и просмотром состояний сообщения.

Если обязательных тестов нет, ревьюер выбирает **Request changes** и ссылается на конкретный критерий issue. Исправления идут в тот же PR, issue остаётся открытым. Отдельный тикет «дописать обязательные тесты потом» не закрывает исходную задачу. CI проверяет результат запуска; полноту сценариев оценивает ревьюер.

## Коммиты: MCGA

Используем [h1km4t1ll0/make-commits-great-again](https://github.com/h1km4t1ll0/make-commits-great-again). Его формат уже опирается на [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/): `feat:`, `fix:`, `docs:`, `test:`, `chore:`, `ci:` и другие типы обозначают смысл изменения.

Текст коммитов — **на английском**. После префикса используем энергичный стиль MCGA, сохраняя точность технического описания. Имена файлов и API сохраняем как в коде. Стандартные сообщения merge-коммитов оставляем обычными.

```text
docs: Setup instructions are FINALLY Clear!

The installation steps were missing. Now README walks through the pinned SDK and native prerequisites. Ready to build!
```

В проект уже включён [skill](../.agents/skills/make-commits-great-again/SKILL.md) с [зафиксированным источником](../.agents/skills/make-commits-great-again/UPSTREAM.md). В поддерживающем project skills агенте он доступен после открытия этого checkout; при установке во время чата — со следующего хода. Для другой среды смотри [инструкцию установки upstream](https://github.com/h1km4t1ll0/make-commits-great-again#readme). Конвенция действует и при ручных коммитах; сам skill — помощник для составления сообщения.
